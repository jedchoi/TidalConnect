# NFR Requirements 계획 - dart-playback-tests

**이 unit 의 NFR 이란**: 이 unit 은 테스트 코드를 만든다. 비기능 요구사항은 앱의 성능 · 가용성이 아니라 **테스트의 품질** (결정성, 실행 시간, 커버리지, 재현성, 유지보수성) 과 **테스트 도구 선택** 이다.

## Question 1 (기술 스택 선택)
Dart 속성 기반 테스트 프레임워크로 무엇을 쓸까요? (PBT-09. 둘 다 사용자 정의 생성기 · 자동 축소 · seed 재현 · `flutter test` 통합을 지원합니다)

A) `kiri_check` 1.4.0 - 지금도 관리되고 있다 (3주 전 배포). 실패하면 seed 를 출력하고 `seed:` 로 그대로 재현한다. 상태 기반 테스트 API 가 있다. 단점: 사용자가 적다 (30일 다운로드 약 6,200), 개발용 간접 의존이 조금 더 많다 (권장)

## Question 2 (신뢰성 · 유지보수성)
속성 기반 테스트의 seed 를 어떻게 할까요? (PBT-08 이 둘 중 하나를 고르도록 요구합니다)

A) 고정 seed - 로컬과 CI 가 매번 같은 입력으로 실행한다. NFR-03 의 "10회 연속 실행 결과가 모두 같아야 한다" 와 맞는다. 관련 없는 커밋에서 CI 가 갑자기 실패하는 일이 없다. 새 입력을 탐색하고 싶을 때는 환경 변수로 seed 를 바꿔 직접 실행한다 (권장)

B) 매 실행마다 무작위 seed - 실행할 때마다 다른 입력을 시도해 시간이 지날수록 더 많은 경우를 본다. 실패하면 출력된 seed 로 재현한다. 코드 변경과 무관하게 CI 가 실패할 수 있고, 그때는 억누르지 않고 조사해야 한다

[Answer]: A (사용자 지시 "추천으로 진행해줘" 에 따라 권장안 기입)

## 질문하지 않은 범주와 이유

- **확장성 · 가용성 · 사용성**: 테스트 코드에는 해당 없음. 앱의 동작을 바꾸지 않는다
- **성능**: 기준이 이미 있다 (NFR-03: 추가 실행 시간 30초 이하). 속성당 실행 횟수는 프레임워크 기본값 100 으로 시작하고, 시간 기준을 넘으면 `fake_async` 조립이 필요한 상태 기반 속성부터 줄인다
- **보안**: 보안 확장은 사용하지 않기로 했다. 테스트 데이터에 실제 토큰 · 키 · 계정을 넣지 않는다는 요구만 문서에 넣는다
- **유지보수성의 나머지**: `CLAUDE.md` 와 NFR-05 가 정했다 (`test/helpers/` 방식, 줄 길이 120). 테스트 이름은 기존 테스트처럼 한국어 문장으로 쓴다
- **`fake_async` 선언**: 선택의 여지가 없다. 직접 import 하려면 `dev_dependencies` 에 선언해야 한다 (위 표)
